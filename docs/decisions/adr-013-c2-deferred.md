# ADR-013: C2（`interface` 消费 / C↔C transfer）暂不立项——维持冻结

## 状态
accepted（2026-10-18）

## 背景

"C2" = 两道被冻结的结构缺口：

1. **`interface` 消费**：resolved 簇在 `_reconcile` 时记录跨簇身份敏感边（parent/child/spouse，去重 + 封顶 32），但**没有任何代码读它**（`overflow_fraction` 的继承溢出是唯一部分消费，且不经 interface）；
2. **C↔C transfer**：通道的 `transfer` 只做 R↔C（L1「边界外」明确：C↔C 族间再分配、resolved 簇支付**不做**）。

本轮探索还实证了 `interface` 数据面的三处缺陷（此前未记录）：只对 **resolved** 簇记录（coarse 簇永远没有新边）；`coarsen` **不清理**（留下陈旧边）；**不随快照**（`ClusterStore.to_payload` 不含该字段，恢复即失）。

## 考虑过的方案

- **方案 A（采纳）维持冻结 + 登记现状**：不改代码；把 `interface` 标为"预留字段"（无消费方 / 不随快照 / 粗化后不清理），并写死重启条件。
- **方案 B（拒）C↔C transfer 原子补全**：通道加 cluster→cluster 的池到池转移。**拒**：无消费方（`RULES` 只有婚配规则、只发 `bind`）——落地即死代码；且把通道从"R↔C 交互面"扩成通用消息总线，与 L1「边界外」的有意范围控制冲突。
- **方案 C（暂缓）`interface` 消费**：跨簇婚配通量 / 继承路由到具体簇等。**暂缓**：消费语义是**产品/模型问题**（要先回答"要什么样的跨簇共演化"），且数据面三缺陷未修——先接线等于给一个半失效的信号供数。

## 选择

方案 A。**重启条件（写死）**：出现以下任一需求时重启评估——① 需要**跨簇质量转移**的规则（赡养 / 分家 / 族间转账）或演示；② 需要**跨簇共演化**的产品诉求（如"亲家之间的往来"）。重启时先修数据面（定义消费方 → 序列化 / 粗化清理），再定消费语义；实现仍须走 ADR + 测量纪律。

## 后果

- **正面**：拒绝为假想需求扩面（通道面与模型语义保持最小）；`interface` 的"看起来在工作"错觉被消除（预留字段醒目化 + 三缺陷登记）。
- **负面 / 边界**：跨簇共演化的表达力仍缺（登记为已知边界）；若未来需求出现，需补一轮数据面修复 + 语义设计。
- **下一步**（真正有驱动力的相邻工作）：**生产注意力轨迹观测**——"滞回默认启用"与"误差触发启用"都卡在"没有生产样态数据"；用现成观测面（`resolution_summary` / SSE `resolution`）在生产样态长跑中采样（测量轮、不改行为）。
