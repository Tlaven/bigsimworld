# ADR-007: 第一条交互规则 = 跨分辨率婚配（R→C，`bind`，默认关）

## 状态

accepted（2026-10-17；实现 = `app/core/measure/rules.py` 的 `MarriageRule` + `SIM_CHANNEL_MARRIAGE` 开关；
步骤级规格见 [`modules/interaction-channel.md`](../modules/interaction-channel.md) N2-7）

## 背景

ADR-003 定的方针是"**先建通道、后定规则**"：通道（`bind` / `unbind` / `transfer`）与守恒/配额/宽限期已就绪，
但第 9 缝 `RULES` 一直为空 ⇒ 通道"通电不做功"，"共演单元"名不副实（只有隔离，没有共同演化）。

第一条规则要满足：① **只用已建好的原子**，不新造守恒协议；② **不碰已冻结的公共面**
（关系漏斗常量、广场、两个 driver）；③ 语义要**配得上"共演"**——真正让两种分辨率之间产生身份边。

可选的四类语义：跨分辨率**婚配**、跨分辨率**结友**、族内**赡养/馈赠**（`transfer`）、
resolved 死亡后的**族内继承**。其中继承会与个体引擎的语义真值冲突（个体引擎死亡只给子女 10%，
其余蒸发；让窗口死者把 90% 给族池等于**改真值**），赡养/馈赠的"谁给谁、给多少"没有现成语义，
结友对家族边界的贡献最弱。**婚配**最合适：`FamilyKind` 的身份敏感边就是 `parent/child/spouse`，
跨分辨率婚配正是"窗口单身与族内单身成婚"这一条**缺失的通量**。

## 考虑过的方案

### 方案 A：R→C 婚配 + 每个单身每 tick 以 `MARRIAGE_RATE` 发起 + 默认关（采纳）
- 发起方只能是 resolved 单身（只有真个体有"意愿"）；`bind` 从目标 coarse 族析出 1 个单身并 `link(..., "spouse")`。
- 强度复用个体引擎的婚配尝试率 `MARRIAGE_RATE = 0.1/360`（与 `Character.step` 每 10 tick 一次的
  `round_up(0.1·τ/360)` **同源**，即每 tick 等效）。
- 默认关（`SIM_CHANNEL_MARRIAGE` 缺省 0）⇒ `RULES` 仍为空 ⇒ 现有权威数字与门槛不动。
- 优点：原子现成、语义自然、可校准、对现有系统零侵入（关时）。
- 缺点：开启后窗口单身的**总婚配风险**上升（窗口自己的婚配事件照常跑）⇒ 这**是**新语义，不再要求与纯个体引擎收敛。

### 方案 B：双向（R→C + C→R）（被拒）
- **拒绝理由**：coarse 侧没有"意愿"（它只是分布）。C→R 只能表现为"族析出一个代表去和某个窗口成员成婚"，
  这个"代表"既非族的选择也非个体的选择——**语义是伪的**。ADR-003 的方向对称是为 `transfer`（质量移动）与
  `bind` 的**表达**服务的，不是为规则语义服务。

### 方案 C：让跨婚配**挤占**窗口内婚配概率（总风险不变）（被拒，留作跟进）
- 优点：最忠实——窗口单身的"总结婚风险"与参照一致。
- **拒绝理由**：要动 `IndividualEvents.spouse_event`（已冻结面）或给它一个"替代口径"，
  属**独立决策**；且它把"窗口学习族内婚配"变成"窗口婚配被族瓜分"，语义更绕。
  MVP 先用"新增通量"的诚实口径，把校准留作后续。

### 方案 D：默认开（被拒）
- **拒绝理由**：会让婚姻/生育/共演单元结构全变，需要重新校准所有门槛与权威数字——那是大改动，不该塞进"第一条规则"。

### 方案 E：先成为熟人再结婚 / 门当户对（财富 Match）（被拒）
- **拒绝理由**：coarse 侧**没有图**，"先熟人"表达不出来（这正是 ADR-003 拒绝 id 式寻址的同一条理由）；
  财富择偶会引入"阶层"这一新语义，而个体引擎的婚配**既无性别约束也无财富约束**——MVP 不引入原因子没有的东西。

### 方案 F：离婚 / 再婚 / 孀居再配的逆操作（被拒）
- **拒绝理由**：个体引擎没有离婚；孀居由死亡事件自然解除配偶边。给规则造逆操作会新开一批不变量
  （`unbind` 的语义是"折算回粗侧"，不是"离婚"），属独立决策。

## 选择

**方案 A。** 关键规则（完整步骤见 N2-7）：

1. **发起方**：窗口内 `18 ≤ age < 60` 且 `relationships["spouse"]` 为空的 resolved 个体；
   **性别中立**（与个体引擎一致）；每 tick 以 `MARRIAGE_RATE` 掷一次。
2. **动作**：`Intent(op="bind", kind="spouse", origin=("character", rid), scope=("cluster", cid),
   match=Match(marital=0, age=(18, 59)))` —— `bind` 先扣后加析出**恰好 1 个**单身（`marital=0` ⇒ `amount=1`），
   `link(rid, new, "spouse")`。**不涉财富**（无彩礼；`transfer` 不参与）。
   区间写成 `(18, 59)` 是因为 `Match` 是**闭区间**，而个体引擎的婚配条件是 `18 ≤ age < 60`（`age=60` 已在死亡流里）。
3. **目标簇**：`level==0`、mini 中存在 `count ≥ 1.0` 且满足上述 `Match` 的桶；
   候选按 `cid` 升序、用注入 rng 做**计数加权抽样**。
   **不做"自家簇 / 亲属避让"**：coarse 簇的 `member_ids` 按契约**必为空** ⇒ 不存在"发起者所属的 coarse 簇"；
   个体引擎本身也没有亲属避让（`relatives` 检查早已删除）。这是**刻意识别差异**，不是遗漏。
4. **不重复婚配**：规则在 `window.step` **之后**运行 ⇒ 本 tick 刚在窗口结婚的人 `marital≠0`，自动跳过；
   规则结的婚下一 tick 窗口事件也会跳过（`spouse_event` 要求 `not relationships['spouse']`）。
5. **配额与宽限期**：照旧由通道执行——`cap_per_tick=8` / `cap_per_cluster=2` / headroom；
   `bind` 成功即登记 `recently_active[coarse_cluster]`（母族在宽限期内分辨率冻结）。
6. **开关**：`SIM_CHANNEL_MARRIAGE`（缺省 `0`）；`=1` 时 runner 才 `register(MarriageRule())`。
7. **语义声明**：开启 = **新增一条婚配通量**。因此开启状态下**不**要求与纯个体引擎收敛；
   `bench.convergence` / `bench.cluster_fidelity` 等门槛一律在 `RULES` 空（默认）下跑。

### 取舍

- 为了**诚实**，接受"开启后不是参照模型的忠实近似"——它是**扩展**，不是近似。这条必须在文档里说死，
  否则下一个人会拿"收敛失败"来质疑规则。
- 为了**不动冻结面**，婚配不经过熟人漏斗：窗口单身直接与族内陌生人成婚（个体引擎是从 `friend`+`familiarity`
  里挑），也不做亲属避让。这是 MVP 的刻意识别差异，记为边界。

## 后果

### 正面后果
- 通道第一次在生产路径上**做功**：窗口与族之间出现真实的 `spouse` 边，共演单元有"共同演化"的内容。
- 零侵入默认：`RULES` 空时逐位一致，全部现有门槛与 `bench` 数字不变。
- 复用全部既有纪律：守恒由通道保证，规则只声明意图；宽限期、配额、账本、确定性一并继承。

### 负面后果
- **开启后不是参照模型的近似**（新增通量，总婚配风险上升）⇒ 需要独立校准（记入跟进）。
- 婚配是"陌生人婚配"（不经过漏斗），与个体引擎的择偶口径不同。
- 没有亲属避让（个体引擎也没有——"亲属避让"检查早已删除）、没有年龄差限制、没有离婚/再婚；
  析出的配偶**不进 `member_ids`**、也不建 `acquaintance` 网（只有 1 条 `spouse` 边）⇒ 在容量压力下是较早退场的对象
  （退出走 `dematerialize`，不是 `unbind`）。
- 规则每 tick 扫一遍窗口单身与 coarse 桶（O(capacity + 簇数×占用桶)），在容量 1000 时约 1e5 次/ tick，可接受但非免费。

### 需要跟进的
- teach-back 对账（独立验证者，判"有缺口但可补"，11 条在实现前补完）：
  [`reviews/2026-10-17-marriage-teachback.md`](../reviews/2026-10-17-marriage-teachback.md)。
- **校准**：`MARRIAGE_RATE` 是"尝试率"，但规则的成功条件（族内有合格单身）比个体引擎（有 `friend`）更宽松 ⇒
  开启后实际婚配速度偏快。要标定就把"窗口已婚比例 / 初婚年龄"作为观测量，与 `SIM_MODE=individual` 对齐后再定 rate。
- **总风险口径**（方案 C）：若校准发现"新增通量"不可接受，再走"替代口径"（碰冻结面，独立 ADR）。
- 亲属/年龄差/财富门第等额外约束；离婚/再婚；`transfer` 侧的彩礼/赠予（可与本规则组合，但要另一条 ADR）。
