# ADR-005: 质量侧 `transfer` = 每粗侧通道池 + 整桶清算/投递（池随生命周期折叠）

## 状态

accepted（2026-10-17；实现 = `app/core/measure/channel.py` 的 `op="transfer"`、`Measure.transfer_pool`、`transitions.deliver_transfer_pool`；步骤级规格见 [`modules/interaction-channel.md`](../modules/interaction-channel.md) N2-6）

## 背景

[`adr-003`](adr-003-interaction-channel.md) 把跨分辨率交互拆成两半：身份侧 `bind`（已实现）与质量侧 `transfer`（当时只登记、不实现）。理由是一道绕不开的量化题：

> coarse 侧的财富只能以 **`count × 桶宽度`** 为最小单位整桶挪动（沿用"整数桶位移"纪律），
> 而具名个体的 `wealth` 是精确浮点 ⇒ 任意金额 `A` 通常**无法**由粗侧精确付出/收入。

若不承接这个差额，财富会被**凭空造出或销毁**。这不是实现细节：它是"质量侧"唯一的正确性风险，且与 `bind` 的人头守恒是**两条独立的账**。

起草规格时又发现一个**既有**的财富漏洞（与 `transfer` 无关，但同一族）：

- `ClusterStore.coarsen` / `merge` / `dissolve` 只折叠 `counts`，**不折叠** `Measure.yearly_inherited`（继承段池余量）；
- 快照 `measure_to_payload` 只存 `cells`，同样丢池余量。
- 其后果在 `bench.audit_ledger --clusters` 里**看不见**——那条审计只守人头，不守财富。任何"财富守恒"不变量都必须先把池折叠补齐，否则新账也会被旧洞污染。

因此本 ADR 要同时回答两件事：**transfer 的残差放哪、怎么结清**，以及**池在共演单元生命周期里怎么活下来**。

## 考虑过的方案

### 方案 A：每个粗侧一个通道池 + 整桶清算/投递（采纳）
- 在 `Measure` 上增加 `transfer_pool: float`（**每个粗侧各自持有**：全局测度一个、每个 coarse 共演单元一个）。
- **R→C**：个体精确扣 `A`，池 `+A`。
- **C→R**：个体精确收 `A`；池够就直接付，不够就**向下整桶清算**（把分布换成池），再付。
- **投递**（settle）：每 360 tick 把池按整桶位移送回分布；余量留池。
- 优点：守恒与确定性收在一处；残差有明确归属（不跨族泄漏）；与继承段池（`yearly_inherited`）同构；可审计到每个粗侧。
- 缺点：池可能长期非零（尤其分布只有 `count` 很大的桶时）；清算会**超取**（见下）；投递策略是 MVP 的任意选择。

### 方案 B：全局单一通道池（被拒）
- 优点：结构最简，一个 float 就够。
- **拒绝理由**：残差会**跨族泄漏**——A 族的量化余量可以付给 B 族，直接破坏"富族恒富"的族内闭合语义（Stage 12 的卖点）。
  对账也无法回答"这笔残差属于谁"。全局池只应作为 `dissolve` 之后的**最终归宿**，不能作为日常容器。

### 方案 C：只允许整桶量级的 transfer，其余拒绝（被拒）
- 优点：完全不需要池。
- **拒绝理由**：`A` 表达不出"给 500"这种自然金额；且 C→R 从 `count=3` 的桶取 1 桶仍是 **3000**，
  不是 1000——"整桶"并不等于"一个人一步"。拒绝率会高到让通道在生产里不可用。

### 方案 D：允许分数桶位移 / 把残差拆进相邻桶（被拒）
- **拒绝理由**：Stage 3 已实测——拆分桶计数使 `occupied` 从 500 膨胀到 19,512、77 ms/step。
  这是被反复否掉的方案，不再重开。

### 方案 E：每笔 transfer 独立 escrow，必须同 tick 结清，否则整笔丢弃（被拒）
- 优点：没有长期池，语义最"干净"。
- **拒绝理由**：绝大多数金额无法同 tick 结清 ⇒ 通道再次变成"通电不做功"；
  且无法表达"族里先攒着，明年给孩子"的跨期 treasury——这恰好是继承/馈赠的常态。

### 方案 F：C→R 只能用已入池的资金，禁止从分布清算（被拒）
- 优点：粗侧分布永不因支付而被改写，语义最保守。
- **拒绝理由**：资产≠流动性。一个"有房没钱"的族付不出一笔小额馈赠，只因为它此前没收过 R→C；
  继承循环（R→C 入池 → C→R 付继承人）能跑，但"族养人"跑不了。需要清算。

### 方案 G：允许负计数 / 凭空造人（被拒）
- **拒绝理由**：`SparseCounts` 的夹零语义与"计数 = 人"是测度层的根；负数/分数人会把人头守恒一起毁掉。

### 方案 H：给 `bind`/`unbind`/`coarsen` 的财富折算也建一个全局"换算残差池"（当时不采纳，留作跟进）

> **2026-10-17 更新**：本条已由 [`adr-006`](adr-006-conversion-residual.md) 采纳并实现
> （形态按符号账、按测度归属，而非"池"）。下面的理由保留为当时的判断。
- 说明：`unbind` / `dematerialize` / `coarsen` 把精确财富折回桶中心，天然有 ≤ `w/2` 的量化差；
  若要做**全局**财富恒等式，这笔差也需要承接。
- **不采纳理由**：它改的是既有分辨率算子的财富语义（且余额可正可负，需要另一套符号池）；
  与本 ADR 的 transfer 池不是同一条账。先按"transfer 原子自身严格守恒"落地，全局口径记为已知边界与跟进项。

## 选择

**方案 A。** 关键规则：

1. **池的归属 = 粗侧**。`transfer_pool` 是 `Measure` 的字段：全局测度与每个簇的 mini 测度各一个
   （`materialize` 保留 mini ⇒ **resolved 簇也可能持池**，其池在 resolved 期间冻结）。
   `dissolve` / `split` 把簇池折进全局池；`merge` / `coarsen` 把池并到目标测度——**池不丢**。
2. **R→C = 精确借记 + 入池**：个体 `wealth -= A`，目标 mini `transfer_pool += A`。不立即改分布。
3. **C→R = 精确支付 + 必要时清算**：
   - 池 ≥ A：直接付，池 `-= A`。
   - 池 < A：先做**向下整桶清算**——把分布里的整桶财富挪进池，直到池 ≥ A；再付。
   - 清算策略（MVP，确定性）：候选桶按 `(count, −wealth_bucket, index)` 升序（**人数最少优先**，并列取更富的桶），
     每个桶取 `k = ceil(缺口 / (count×w))` 步、且不越过桶 0；按**源桶财富升序**应用位移（避免级联重复扣减）。
   - 超取部分留在池里（属该粗侧），以后由 settle 归还分布。
     **超取上界 = 被清算桶中最大 `count × w`**——"人数最少优先"只减少被触及的桶数，
     最后一个被命中的桶可能 `count` 较大（反例 `1@5 + 3@6` 付 6000 ⇒ 超取 2000）。
4. **投递（settle）= 每 360 tick**：把池按整桶位移送回分布，**最穷桶优先**（MVP 的再分配口味），
   每桶 `k = floor(池 / (count×w))`，受财富上限约束；按**目标桶财富降序**应用位移；余量留池。
5. **池非负**：所有操作只可能加池、或"先保证池够再减池"；不存在负池。
6. **不改身份、不占配额、不给宽限期**：transfer 不析出、不建边、不改窗口容量；`cap_per_cluster` / `cap_per_tick` /
   headroom 只约束 `bind`。transfer 也**不**登记 `recently_active`（没有需要保护的新身份）。
7. **只对 coarse 簇**：resolved 簇没有聚合态，`transfer` 命中 ⇒ `dropped:stale`；
   C↔C（族间再分配）本期**不做**（没有身份侧，不需要通道的 `bind` 机制；需要单独的路径与策略）。
8. **R→C 不接受 `Match`**：R→C 的对手方是显式 `cluster`，没有"粗侧寻址"需求；非空 `Match` ⇒ `dropped:unsupported_match`。
   C→R 的 `Match` 只用于**选接收者**（窗口角色，按 `id` 升序取第一个匹配）。
9. **财富恒等式**（transfer 口径）：
   ```
   W = Σ 粗侧 count×桶中心 + Σ transfer_pool + Σ yearly_inherited + Σ 窗口个体 wealth
   ```
   `transfer` / 清算 / 投递 / 池折叠都是 **W-中性**（精确到浮点）。
   注意：`bind` / `unbind` / `dematerialize` / `coarsen` 的**桶中心折算**仍有 ≤ `w/2` 的量化差（方案 H，已知边界），
   所以全局 W 的严格恒等式只在"无分辨率折算"的区间内成立；transfer 原子自身不受此影响。

### 取舍

- 为了**归属清晰**，牺牲了"一个池就够"的简单性：要维护 N 个池，并在生命周期算子处逐处折叠。
- 为了**能用**，接受清算超取：一次 C→R 可能让某个粗侧桶的居民整体变穷/变富，多于/少于实际支付；
  超出的部分留在池里，误差有界（**被清算桶中最大 count × `w`**）。
- 为了**确定性**，投递/清算顺序都是排序后的固定顺序，不允许"按 dict 迭代顺手挑"。

## 后果

### 正面后果
- 质量侧有了**可执行的守恒口径**：每笔 transfer 都能在账本上核平，池余额可观测、可断点恢复。
- 补上了 `coarsen` / `merge` / `dissolve` / `split` / 快照**丢池**的既有漏洞（含 `yearly_inherited`），
  并把 `merge` 的 resolved+resolved 快路径纳入折叠范围（那里原本连**计数残留**都会丢）。
- 与继承段池同构：同一套"整数桶位移 + 余量留池"纪律，不新造第二套守恒协议。

### 负面后果
- ~~**全局 W 不严格**：分辨率折算的 ≤ `w/2` 量化差仍在（方案 H 未做）~~ **已由 [`adr-006`](adr-006-conversion-residual.md)
  接管并修复**（符号残差账；`bench.audit_ledger --wealth` 逐算子守）。
- **清算会改写分布**：C→R 可能让 `count` 大的桶整体移动一档；这是"粗侧只有分布"的必然代价，不是 bug。
- **投递策略是 MVP 口味**（最穷桶优先）：会给分布带来轻微的累进再分配；将来要换策略需另立 ADR。

  C↔C 与 resolved 簇支付仍未做。

### 需要跟进的

- 方案 H：分辨率折算的符号残差池，若将来要做**全局**财富恒等式，必须先补它。
- 投递策略可插拔（`PoolPolicy`），以及"是否保留流动性储备"的参数化。
- 规则注册表的第一条真实语义（婚配/结友/继承）仍需独立 ADR。
