# Glossary — 术语表(项目级)

> **使用方式:** 项目引入"领域专有名词 / 自定义概念 / 易混词"时创建并维护本文件。
> 目的:AI 不认识你的领域黑话。**一个词只在这里定义一次**(单一事实来源),文档别处只引用、不重述。
> 判据:读者(AI 或新人)看到这个词,能否**不看代码**就知道它指什么、结构是什么、边界在哪。

---

## 为什么需要(而不是可选)

LLM 是"模式补全器",不是读心术。**你没定义的词,它会拿训练数据里的通用含义去猜**——在 AI 没见过的领域里,这必然错,且往往错到实现深处才暴露。

**反过来:AI 老用模糊词(「优化」「合理处理」「相关逻辑」),通常是你没给它可判定的指称物,不是它笨。**

|---|---|---|---|---|---|---|
| <!-- 例:标识符 --> | <!-- 例:唯一标识一个模型元素的字符串 --> | <!-- string,形如 `<graph>.<node>` --> | <!-- `g1.user` --> | <!-- 不是变量名;不含空格 --> | <!-- 别叫"ID" --> | <!-- 例:出自 README「数据模型」节 --> |

**字段说明:**

- **定义**:一句话,描述**它是什么**,不是它怎么实现
- **类型 / 结构**:AI 生成代码时最需要的一栏(数据类型、形状、取值范围)
- **例子**:一个**精确**的正例(能直接当 fixture / 测试输入用)
- **反例 / 易混**:最容易跟哪个词混?为什么不是它?——**挡错误理解比给正例更有效**
- **禁用别名**:历史上用过、但已废弃的称呼(防止 AI 从旧资料里捡回来)
- **出处**:词条从既有作者文档 / 代码提取的,**标来源**;靠推断补的,标 `推断,待确认`——与"证据 vs 编造"一致。若两代术语并存(旧词未正式退役),在定义里**标代际**(如 v1 / v2)

> **与验收挂钩**:本表的「例子」栏正例就是 N2 验收的 fixture——
> 一处定义、两处使用(术语表 ↔ `docs/core-code.md` / L2 的 `[不变量]` 架构级约束 / `docs/modules/<name>.md` 的 N2 `**验收**` 栏)。
> 别在两边各写一份,否则必然漂移。

## 去模糊词表(可选,但推荐)

项目里**禁止**出现的模糊表述 → 换成可判定的写法:

| 禁止写法 | 换成 |
|---|---|
| "合理处理错误" | "输入 size > X 时抛 `SizeExceeded`" |
| "优化性能" | "P95 < 200ms" |
| "相关逻辑" | 点名具体函数 / 模块 |
| "适当的时候" | 写出触发条件 |
| "结果要稳定 / 可复现" | "钉住全部输入(数据 + 配置/合同版本 + 引擎版本);同一输入 → 逐字节一致(或指定数值精度)" |
| "要准 / 不能算错" | "列出精确例子(输入 → 输出),并写出计数守恒等式" |
| "间距要好看 / 体验要顺" | 落到**至少一个可测代理指标**(如最小间隙 ≥ X、无重叠),并标 `候选(待否决)`——**候选 = 可被否决的提案：在你确认前只能当候选引用，不能当结论**(否决理由进 ADR) |

## 对话地图(和用户对话时问什么)

- 这个项目里有没有**外人听不懂**的词?(行业黑话、你自定义的概念)
- 哪些词**最容易混**?(记下来当反例)
- 有没有**旧叫法**已经被废弃?(记下来当"禁用别名")
- 哪些词,AI 要生成代码时**必须知道它的类型 / 结构**?

---

## 维护规则

- 出现**新领域概念** → 当场登记,再在别处使用。**登记时自问:这个词描述的是领域特有的新行为,还是给通用做法起的新名?** 前者 → 所在单元按 **N2** 处理(模型对它有一个通用含义、而且往往不止一个);后者 → **不因此加分档**(基线仍按 L1 铁律 7 起评)——词的风险由词条本身承担(定义 / 类型 / 例子 / 反例)。
- 文档里出现**未登记的名词** = 漂移信号:补齐,或改用已登记词
- 术语含义变化 → 视为可能的不变量变更,走 ADR(方式同演化期规则 E3)
- 一个词只在一处定义;别处只引用——重述必然产生第二个定义,迟早打架
