# 演化期规则(E1–E7)——立项之后,文档怎么不死

> **本文件是 E1–E7 的唯一归属**,随项目落地到 `docs-templates/evolution-rules.md`。
> L1 记忆文件只留指针;子文档、决策记录、代码注释都不重述,必要时只指针回这里。
> **何时读:** 做文档演进 / 对账 / 大改动前。

**先看总表**——三段式是"容器";每段里的陈述按**性质**分四类,腐烂方式与维护动作各不相同。E1–E7 是这张表的分项细则。

| 性质 | 真相源 | 会怎么烂 | 维护动作 | 细则 |
|---|---|---|---|---|
| **描述型**(现状) | 代码 | 变假 | 降为指针优先;改代码后同步;**不留尸体** | E1 |
| **决策型** | 历史 | 悬置 | 只增不改;被推翻 → 标 `⚠️` 保留原文;该记才记 ADR | E1 / E4 |
| **约束型**(不变量) | 契约 | 被悄悄违反 | 每条标 **强制 / 约定**;违反 → 三选一 | E3 |
| **方向型** | 承诺 | 悬置 | 状态机 `planned→doing→done/dropped`;集中安置 | E2 |

## E1: 描述型——陈述退役,[是什么] 不许有尸体

- **[是什么] 段是"现状快照",不是历史博物馆。** 某事实不再成立时,直接改写或删除,**禁止**留旧陈述与新陈述并存(哪怕标注"旧的"),并存 = 读者不知道信哪个。
  > **限定:** "不留尸体"**只针对描述型**。**决策型**被推翻要保留原文 + 标 `⚠️`(下一条),**方向型**(E2)保留状态——这两类不算尸体,别删。
- **降为指针优先于重建**:能从代码 / git 验证的事实(文件清单、函数名、参数表),不抄进文档——抄写必然漂移,指针(见 `src/`、见主流程叙述)永不腐烂。文档只留代码里**读不出来**的事实(边界、数据流方向、协作契约)。
- **[为什么] 段的决策论述被推翻时,必须显式标注状态**,格式:`> ⚠️ 已被 vXXX 推翻,见 ADR-YYY`(一行,保留原文)。要"历史"就去读 ADR / git,[为什么] 正文里的每句话都应是仍然成立的。
- 修改 [是什么] 时顺手检查同文件 [为什么]:两者矛盾 = 有人只更新了一半,当场修掉。

## E2: 方向型陈述与状态流转——意向不搬家就悬置

- 三段式内容实际混合了不同**性质**的陈述(见上表四类),腐烂方式各异:**描述型**说现状(真相源 = 代码,会变假)、**决策型**(真相源 = 历史,只增不改,走 E1 supersede)、**方向型**说意向("计划做 X""需要跟进"),真相源 = 承诺,**不会变假,只会悬置**——没人知道它是 planned、已做完还是已放弃。

方向型最容易混进 [是什么] 伪装成事实。治理:

- **集中安置**:方向型陈述只活在少数固定位置(ADR"需要跟进的"段 / L3"实现方向" / ROADMAP 小节),状态只在有数的地方维护。散落在事实段里的方向性内容就地清除。
- **状态流转**:planned → doing → done / dropped。**done 移出**:完成的方向不再留在活跃清单(历史在 git);"带理由的 dropped"往往应升格为决策型("不做 X"是约束,走 ADR)。
- 方向性陈述在 [是什么] 里裸留(无状态、无集中安置)= 尸体的另一种形态,对账(E5)时同样清。

## E3: 约束型——推翻不变量 = 必须走 ADR + 修订原文

- 不变量是一次性对话产物,会随功能演化过时。**任何一次改动若与现有不变量冲突,必须三选一并执行**:修订 L1/L2 里的不变量原文、给不变量加例外说明、或放弃该改动。**禁止**只改代码不动文档——那是不变量失效的开端。
- 推翻重大不变量的改动(如"标识符必须 ASCII"→ 允许 Unicode)必须升格为 ADR,哪怕当时觉得"顺手改的"。
- 判据:**当你会说"这条不变量过时了"时,就是 ADR 触发点。**
- 联动义务(标 superseded 只算 50%):① 改 L1/L2/L3 正文里引用旧决策的段落,加 `> ⚠️ 已被 ADR-YYY 推翻`(不删原文);② 修订相关不变量;③ 在新 ADR 的"后果"段记下这两步是否完成。

## E4: 决策型——ADR 触发粒度(用"惊讶度"判断,不用"规模"判断)

- **必记**:改完之后让后来者"惊讶"的决策(为什么不用 X?为什么这么绕?)——惊讶就是被拒方案没被记录的症状
- **必记**:推翻先前决策 / 引入第二套并行机制 / 改变数据模型身份语义
- **必记**:养出"两套并存物"的决策(两个同名函数、两种标识符规则、两条数据通路)——并存物必须有 ADR 解释区别,否则下一个人会删错一个
- **不记**:单纯的新功能、bug 修复、重构(代码即真相)

## E5: 对账——文档与代码的周期性一致性审计

- **触发式**:每次版本级变更(vXXX)合并前,对照检查本次改动触碰的模块,其 L1/L2/L3 文档、不变量、以及外部 AI 接口文档(如有)是否需要同步。外部接口文档失真代价最高。
- **集中式**:每隔几个版本做一次"文档考古":通读 L1 记忆文件 + `docs/architecture.md`,凡与代码现状不符的陈述当场修正;发现"文档说有但代码没有 / 代码有但文档说没有"的,修文档并记下当初漏更新原因。
- **产出落档**:每次对账(含 teach-back 与"文档考古")写一份到 `docs/reviews/YYYY-MM-DD-<主题>.md`;并改文档本身;若漂移暴露流程问题,把对策写进 L1 记忆文件。

## E6: 代码注释与文档的分工

- **代码注释不写版本变更史**(如"v0.13 从 io.js 迁入")——那是 ADR / git log 的职责,双轨记录必然漂移。文件头注释只写:该文件的角色定位 + 读者必须先知道的契约。
- 判断标准:注释内容若能在 `docs/decisions/` 或 git log 里找到,就不要写在代码里;注释里只留"读这段代码前必须知道的坑"。

## E7: 术语表是新词的唯一登记处

- 出现**新领域概念** → 当场登记进 `docs/glossary.md`,再在别处使用。
- 文档里出现**未登记的名词** = 漂移信号:要么补登记,要么改用已登记词。
- 术语**含义变化** → 视为可能的不变量变更,走 E3。
- 一个词只在一处定义(单一事实来源);别处只引用,不重述——重述必然产生第二个定义,迟早打架。
- **找不到词先报作者**:要表达一个概念却没有现成词时,先报出(概念 + 拟词 + 拟定义),作者同意后再登记使用;**未获批前不自造词**——自造词必与既有词打架。
- **术语退役 / 改名**:宣布全库退役前**必须 grep 实测**(范围 = `docs/` 全部 + 相关页面 / 脚本的中文叙述),**命中不为 0 不得宣布完成**;退役的豁免(历史原话作证据引用 / 被要求保持原样的件)逐条记进 ADR。
