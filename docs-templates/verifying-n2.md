# 给 N2 造验收（新领域没有 oracle，得亲手造）

> 适用：`docs/core-code.md`、`docs/modules/<name>.md`,以及跨模块逻辑落在 L2 公共节时的 `docs/architecture.md`「架构级约束」——凡标记为 **N2（AI 未见）** 的单元。
> **N0 / N1 不用读本文件**——模型训练数据里有现成的惯用测试写法，自己能写。

## 为什么单独教

N0 / N1 的代码，模型见过大量同类测试；**N2 没有**——而且**你也没有 oracle**（连"正确答案"长什么样都还不知道）。
于是 N2 的风险不是"忘了写测试"，而是"**测试写了假**"：

- 拿实现自己的输出当期望（**循环自证**）；
- 断言同义反复（`result == result` 换个写法）；
- 只测 happy path，不测边界 / 失败分支。

这类假测试**没人能靠肉眼看出来**，所以必须用能识破它的手段。这也是 N2 与 N0/N1 在验证上的分水岭。

## 五种手段（按对"无 oracle"的替代力排序，选 1~2 种）

1. **不变量 → property test**（首选）
   - 把每条不变量写成"任意合法输入下恒成立"的断言。
   - 这是 N2 **唯一可靠的 oracle 替代品**。
   - 例：`∀ order, slots: 返回非 None ⇒ slot.used + order.weight <= slot.capacity`
   - 工具：hypothesis(py) / fast-check(js) / proptest(rs) / QuickCheck 类。

2. **mutation testing**（验"测试本身是否有效"）
   - 故意改坏实现，看测试会不会变红。红不了 = 这测试没用。
   - 专杀循环自证 / 同义测试。
   - 工具：mutmut / Stryker / cargo-mutants。

3. **approved scenario / golden fixture**（冻结期望）
   - 人工确认过的"输入 → 输出"冻结起来；之后被破坏就必须**重新批准**。
   - 可直接复用 `docs/glossary.md` 的 [例子] 栏正例——**同一事实一处定义**（术语表例子 = 验收 fixture）。

4. **盲测验证者**（独立找反例）
   - 一个**看不到实现**、只按文档用系统的人 / agent，专门找反例。
   - 复用同目录的 `teach-back-verifier-prompt.md`（同一套独立验证思路）。

5. **differential**（对照）
   - 有旧实现 / 参考实现时，做输出对照。

## 危险实现清单 = 现成的变异体(优先用这条)

`[不变量]` 段那张「危险实现清单」不是文档装饰,它就是 mutation testing 的**现成变异体**:把"最可能被写成的错样子"真的写出来(或临时改坏实现),看测试红不红。

- 红 → 这条错法已被挡住,把证据写回该清单的「由谁挡住」列(推荐直接写挡它的断言 / 用例;别删行——清单是契约,删行就等于少了一条挡它的规则);
- 不红 → **不是实现错了,是验收不够**,回去补断言。

这比随机语法变异命中率高得多——变异体来自"模型真的会这么写",不是随机扰动。

## 先跑一次，再写进契约（契约断言通则）

**要写进契约的断言**（不变量 / N2 步骤级说明 / 危险实现清单 / 失败语义 / 性能预算），只要**跑一下就能证伪**，就先花十行脚本跑一遍——**跑得出反例的，不许写进契约**。"任意情况下都成立"的（property 型）尤其如此：写之前先写十行脚本跑随机输入。

- 跑得出反例 → 这条断言不成立，别写；改成"近似相等（给出容差）"或改写断言。
- 跑不出、但你也不确定 → 在契约里标 `经验证：<脚本路径> N 组无反例（YYYY-MM-DD）`，说明它是经验性的，不是定理。
  - **脚本别丢**：试跑脚本推荐直接长成那条 `**验收**` 的一部分；不留的，就放固定位置（如 `tests/probes/`）并在标记里写路径——**没有可复跑的脚本，"经验证"只是一句声称**。
- **不能试跑的断言**：至少要能说明它"靠什么站住"（外部来源 / 人的裁量）；两样都没有 → 别写成契约，降级为假设 / 开放问题，或明确标注"未验证"。

**为什么**：试点里一条"分两次结算 = 一次结算"的半群断言，文档层面读起来毫无破绽，实测 **53% 的随机整数对不成立**（浮点除法 + 加法不满足结合律）。teach-back 读不出这种错——它只能验"写得清不清"，验不了"做不做得到"。**这一类错只有外部核实（试跑 / 来源）拦得住。**

## 反模式（必读）

- ❌ 测试拿实现自己的输出当期望（循环自证）
- ❌ 断言同义反复
- ❌ 只测 happy path
- ❌ 把"有测试"当成"测试有效"
- ❌ 文档声称"已验证 / 全绿"，却没有可复跑的命令 / 脚本（或没标"未接 / 未复跑"）——**声称不是证据**；"未接 / 未复跑"标记就写在该声称旁边。

## 闸门

若某条 N2 逻辑**造不出可跑验收** → 不是"测试先欠着"，而是说明**逻辑还没讲到可实现**：
回去补 `[步骤级说明]`（core-code / L2 公共节 / L3），**别放行实现**。

> 这道条件管的是"这条逻辑还没讲到能被实现"，**与 teach-back 跑不跑无关**——teach-back 是按需工具、不阻塞实现（见 SKILL 的 Step 3.5）。

## 写进文档

在 N2 单元的 `**验收**` 栏里写清：

- 命令 + 预期（`pytest tests/test_x.py` → 通过）；
- 或断言（property 形式的不变量）；
- 并注明用的是上面哪 1~2 种手段。

> 写成什么样（`novelty=N2` 字面量 / 一行 `**验收**:…` / 指针形）见 `docs-templates/module-doc.md` 的 N2 说明；检查器只做**字面 / 形式**粗检（清单与边界见 `docs-templates/wiring.md`）。
> **它只查形式、判不了语义**：凑一个 `**验收**` 字样就能骗过它，验收是否真有意义、错法是否真被挡住，仍归 teach-back 验证者。**"检查器过了"≠"验收对了"。**
