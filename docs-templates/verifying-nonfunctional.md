# 给非功能 / 主观需求造验收（"要稳定 / 要快 / 要好看"怎么变成可判定）

> 适用：需求里出现**确定性、性能、审美、安全合规**这类"听着都对、没法判对错"的要求。
> 判据：**能不能写出一条会失败的检查**。写不出来 = 需求还没定义，不是"实现时注意点"。

## 为什么单独教

功能性需求有现成的验收形态（输入 → 输出）。非功能需求没有：
"结果要稳定"无法断言，"间距要好看"没有 oracle，"要快"在谁的机器上都不同。
**于是最常见的失败不是没做，而是做了一个"看起来达标"的版本**，而验收栏里写着"人工确认"。

## 四步转换（任何一类都走这四步）

1. **钉住输入**：这条性质在**哪些变量固定**时才成立？（数据 / 配置或合同版本 / 引擎版本 / 字体与 DPI / 硬件与并发度）
2. **选可观测量**：换成能测的数或能 diff 的产物（字节、耗时分布、字段集合、几何量）。
3. **定比较方式**：相等 / 逐字节 / 分位数阈值 / 单调 / 覆盖性 / 人工批准冻结（approved）。
4. **写成验收**：命令 + 预期，或 property 断言。**必须能失败**——先问"它在什么情况下会红"，答不上来就重来。

## 分类对照表

| 需求原话 | 必钉住的输入 | 可观测量 | 验收形态 | 常见错法 |
|---|---|---|---|---|
| "结果要稳定 / 可复现" | 数据 + 配置/合同快照 + 引擎版本（+ 字体/DPI/随机种子/时区库版本） | 产物的字节或规范化序列 | 同输入双跑 → `diff` 为空；跨版本重算 → 结果不变 | 只测"两次跑差不多"；把随机数、当前时间、字典序当无关变量 |
| "要快 / 不能卡" | 数据规模 + 并发度 + 运行环境 | 耗时**分布**（P50/P95/P99），不是单次 | 基准脚本 + 分位数阈值；回归时对比基线 | 用一次 `time` 当验收；不固定规模与环境；只测空数据 |
| "要好看 / 体验要顺" | 输入样本集 + 渲染参数 | 代理指标（最小间隙、重叠数、行数、字距差） | 代理指标断言 + approved fixture（人工批准后冻结） | 直接写"人工确认"；拿实现自己的输出当期望 |
| "要安全 / 要合规" | 威胁模型或条款清单 | 字段集合、权限矩阵、日志条目 | schema 校验 / 权限矩阵表驱动 / 审计字段存在性 | 只写"做了鉴权"；只测正例 |
| "不能算错" | 边界样本 | 精确例子 + 守恒等式 | 输入→输出表 + 计数/能量守恒断言 | 例子只有名字没有数；例子没人复算 |

## 审美类的最小可行做法（唯一允许"主观"的地方）

审美没有 oracle，但**可以冻结**：

1. 让用户在**少量候选**里挑（≥2 个，各自标注代价）——选型过程本身就是决策记录（进 ADR）。
2. 把选中的结果做成 **approved fixture**（输入 + 期望产物），之后被改动必须**重新批准**。
3. 同时写一条**代理指标**兜底（如"任意两字最小间隙 ≥ 2pt""无重叠"），否则 fixture 一换就没人知道底线在哪。
4. 代理指标标 `候选(待否决)`，直到用户确认。

## 反模式（必读）

- ❌ **"人工确认"当验收**——它没有失败条件，也不会有人真的每次确认
- ❌ **单次计时当性能验收**——噪声比差异大
- ❌ **"尽量一致"当确定性验收**——"尽量"不可判定
- ❌ **只测 happy path 的合规**——权限/审计的错都在负例里
- ❌ **审美只留图，不留代理指标**——后续改动没有任何约束可依

## 闸门

某项非功能需求**造不出可失败的检查** → 不是"验收先欠着"，而是**这条需求还没定义**：
回到对话里把它降成"钉住哪些输入 + 哪个可测代理指标"，或登记进「开放问题」交人拍板。**别放行实现。**

> 这道条件管的是"这条需求还没定义"，**与 teach-back 跑不跑无关**——teach-back 是按需工具、不阻塞实现（见 SKILL 的 Step 3.5）。

## 写进文档

在对应层（项目级 → L1 不变量；架构级 → L2；模块级 → L3）的 `[不变量]` 段写：

- 钉住的输入（一句话列出全部变量）；
- 可观测量的**具体数值或比较方式**；
- `**验收**: <命令> → <预期>` 或 property 断言；
- 若用了 approved fixture：写明**谁在何时批准**（批准人 + 日期）。
