# bench —— 无头性能基准（Phase 1）

这一层**完全不依赖 Web / Redis / 多进程 DB**：用空队列 `SinkQueue` 顶替 DB 写入，直接驱动 `engine.step()`，用于测量"人口规模 → 每步耗时 / 内存"的扩展曲线，并定位热点。

## 脚本

| 脚本 | 用途 | 命令 |
| --- | --- | --- |
| `bench.run_scaling` | 扫描多个人口规模，输出扩展曲线到 CSV | `python -m bench.run_scaling --engine legacy --sizes 1000 2000 5000 10000 20000 --steps 30 --warmup 5` |
| `bench.profile_step` | 用 cProfile 找 `engine.step` 的热点函数 | `python -m bench.profile_step --n 10000 --steps 30 --top 20` |
| `bench.world` | 用固定随机种子构造 N 个角色的引擎（可复现），`engine="legacy"｜"event"` | `from bench.world import build_engine; build_engine(1000, seed=42, engine="event")` |
| `bench.measure` | 逐步计时 + RSS 采样，返回 `avg/p50/p95/max` | `from bench.measure import measure_steps` |

结果默认写入 `bench/results/`。

## 基线结果（Python 3.12.4 / Windows / 单核，seed=42，1000–20000 人）

| N | avg_ms | p50_ms | p95_ms | rss_MB | 每千人 µs |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.367 | 0.187 | 2.00 | 65.2 | 0.367 |
| 2,000 | 0.706 | 0.366 | 3.62 | 69.8 | 0.353 |
| 5,000 | 1.787 | 0.990 | 9.01 | 79.0 | 0.357 |
| 10,000 | 3.856 | 1.891 | 22.1 | 97.0 | 0.386 |
| 20,000 | 9.516 | 3.937 | 63.0 | 130.0 | 0.476 |

## 怎么解读

1. **耗时随人口近似线性，且略偏超线性。**
   每千人耗时从 0.353µs（2k）升到 0.476µs（20k），到 2 万人时人均成本比 1 千人时高约 **35%**。也就是说：人口越多，不是"每人成本恒定"，而是**越跑越慢**——因为 `event_plaza` 的全局洗牌和关系链表操作会随规模放大。
2. **耗时是尖峰式的（spiky）。**
   `p50` 远小于 `avg`、`p95` 却是 p50 的 10 倍以上（2 万人时 p50 3.9ms vs p95 63ms）。原因是 `possible_events()` 每 10 tick 才触发一次，**每 10 步里有 1 步是"重事件步"**，其余是便宜的属性步。
3. **内存线性增长，约 3.2 KB / 角色。**
   65MB → 130MB 对应 0 → 20000 人。外推：10 万人 ≈ 0.4GB、100 万人 ≈ 3GB，单进程必 OOM。
4. **热点排序**（`profile_n10000.txt`）：`Character.step`（全量遍历）> `possible_events` > `round_up_probability` > `random.shuffle`（`event_plaza` 全局洗牌）。

## 结论（这就是 Phase 2 的依据）

> **每步成本 ∝ 人口**，而这个世界的人口只会增长。因此当前模型**在数学上无法长期演化**：跑得越久人口越多，每步越慢，最终必然卡死或 OOM。

- 1 万人 ≈ 3.9ms/步；20 万人外推 ≈ 0.1s/步；千万级即秒级。
- 与 Web 层无关——瓶颈在仿真内核本身。

## 下一步（Phase 2 接口约定）

Phase 2 将把"全局同步 tick"改为"离散事件调度"：给每个体维护 `next_event_time`，用堆（heapq）只处理"下一次真正要发生的事"。目标是把成本从 **∝ 人口** 降到 **∝ 事件数**，让闲置个体零成本。

**Phase 2 完成后必须重跑本文件的基线命令做对比，验证人均耗时不再随人口增长而上升。**

# Phase 2：离散事件引擎（已完成）

实现于 `app/core/simulation/event_engine.py`（`EventEngine`）。它**复用同一套 `Character` 与事件类，只替换驱动器**：为每个角色按自身相位调度 `LIFE`（周期 `step_threshold`）、`WEALTH`（30）、`AGE`（360）三类事件，用最小堆 `(time, 角色插入序, 优先级)` 只处理"到点"的事件。

## 正确性：与原引擎逐位一致

`tests/test_event_engine.py::test_event_engine_matches_legacy` 验证：同一随机种子下，200 人跑 300 步，两引擎的 `(时间, 人口, 年龄总和, 财富总和, 好友关系数)` **完全相等**。即离散事件调度在改变驱动方式的同时，**没有改变仿真语义**。

## 对照结果（每配置独立进程，重复 3 次取中位；seed=42，30 步，2026-10）

| N | legacy avg_ms | event avg_ms | 提速 | legacy p95 | event p95 | legacy MB | event MB |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.403 | 0.262 | **1.54×** | 0.68 | 0.39 | 64.7 | 66.4 |
| 5,000 | 1.938 | 1.567 | 1.24× | 2.7 | 2.1 | 74.5 | 82.2 |
| 10,000 | 4.021 | 3.419 | 1.18× | 5.8 | 4.7 | 86.5 | 101.8 |
| 20,000 | 9.244 | 7.535 | **1.23×** | 22.8 | 10.4 | 111 | 141.3 |

> 实现要点：① 每个角色在堆中只有**一个**待办事件（下一次 wake = 个体事件/财富/年龄三路周期的并集），把"每角色 3 个堆条目"的堆流量降下来；② 把共享的 `round_up_probability` 短路、`move_temp_set` 去权重；③ 把广场配对从"整体 `random.shuffle`"改成 **O(配对数) 的随机抽样腾挪**（`random_pairing`），配对数量与残留量保持不变。三项都对两个引擎生效，因此逐位一致性仍成立。

## 关键结论（一个重要的"负结果"）

1. **离散事件调度没有改变渐近瓶颈。** 大规模下只提速约 1.1–1.2×，并且内存多约 27%。
2. **原因：真正的瓶颈不是"驱动器"，而是 `possible_events()` 的调用频率与单次成本。** 每个"活跃"角色每 10 tick 就必须掷一次骰子，两种引擎都是每 tick `≈ N/10` 次 `possible_events`；单次 `possible_events`（含多次掷骰 + 关系链表操作）约 5µs，**远大于**旧引擎每 tick 全量扫描的开销（约 0.4µs/人）。DS 省下的扫描开销基本被驱动开销抵消。
3. **DS 的可见收益是"削峰"与稀疏世界**：20k 人时 `p95` 从 ~26ms 降到 ~11ms（不再有"每 10 tick 一次的重事件尖峰"）；小规模/稀疏世界时钟可跳过大量空 tick（1k 人 1.41×）。
4. **教训：优化前先找瓶颈。** "事件驱动 = 更快"是常见误判——当每个体都有一条密集的周期事件流时，DS 并不比同步扫描快多少。

## 这意味着 Phase 3 应该做什么

既然瓶颈是"每个活跃个体每 10 tick 必须掷骰 + 维护关系链表"，下一阶段的杠杆是**降低单次交互成本、并减少无效掷骰**，而不是再优化调度器：

- **交互局部化**：把 `event_plaza` 的全局 `random.shuffle`（热点排名靠前）换成局部邻域抽样，去掉 O(规模) 洗牌；
- **减少无效事件**：儿童/老人等不可能触发某些事件的状态，跳过对应判定；
- **数据布局**：对象图 → 数组（SoA）+ CSR，消除每角色沉重的 Python 对象（这也是内存 +27% 的根源）。

> 结论已存入 `bench/results/scaling_legacy.csv` 与 `scaling_event.csv`。

# Phase 5：稀有事件降频（sampled next-event）

## 动机（先测量，再动手）

对事件引擎做了"事件发生率"统计（20k 人，200 步）：

| 指标 | 数值 |
| --- | --- |
| `possible_events` 调用 | **1994 / 步**（≈ N/10，每个活跃个体每 10 tick 都被评估） |
| 结识（acquaintance）触发 | 高频（每次几乎都往广场丢自己） |
| familiarity 触发 | 4.38% 的调用 |
| friend 触发 | 0.11% |
| spouse 触发 | 0.05% |
| childbirth 触发 | 0.39% |
| death 触发 | 0.03% |

即**约 95% 的评估什么都没发生**——这是巨大的浪费。于是把稀有事件从"每 10 tick 评估一次"改成"每 `K` 次评估一次、单次概率放大 `K` 倍"（近似二项/泊松累积），长期发生率保持不变，评估次数降到 `1/K`。

- `rare_stride=1`：**与原引擎逐位一致**（`test_event_engine_matches_legacy` 仍通过）。
- `rare_stride=10`：**接近统计等价**（同种子 5000 人跑 500 步：人口 +0.4%、familiarity +3%、friend −6%、财富 ~0%）。

## 对照结果（`rare_stride=10` vs legacy，独立进程、中位）

| N | legacy avg_ms | event(rs=10) avg_ms | 提速 | legacy p95 | event p95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.390 | 0.191 | **2.04×** | 0.58 | 0.36 |
| 5,000 | 2.02 | 1.20 | 1.68× | 2.8 | 2.1 |
| 10,000 | 4.10 | 2.99 | 1.37× | 6.1 | 6.0 |
| 20,000 | 9.42 | 6.26 | **1.51×** | 22.8 | 11.6 |

`stride` 调参：5 → 10 提升明显（20k：6.17 → 6.04ms），20 反而略差（结识已成为主导，继续降频无收益）。

## 但仍然没有突破 O(人口)

即使降频 10×，**每个成年人仍会被"结识"进程每约 10 tick 唤醒一次**，所以每 tick 的评估数依旧是 `≈ N/10`。降频只是把每次评估**更便宜**（少数评估帧），并未减少"唤醒"本身。**要真正突破 O(人口)，必须改变模型**：让绝大多数个体在绝大多数时间"无事件可做"（例如交互局部化/降低基础社交活跃度），或走 Phase 5+ 的数组/编译下沉走常数因子。

> 对照数据：`bench/results/scaling_legacy.csv` 与 `scaling_event.csv`；命令加 `--rare-stride 10`。

# Phase 6：空间局部化（per-cell plaza）

把 `event_plaza` 从"全局一个池子"改成**按空间格子分区**（`n_cells`，`event_plaza['acquaintance']` 变成"列表的列表"），结识只在**同一格子内**配对。`n_cells=1` 时与原行为**逐位一致**（等价性测试保留），`n_cells>1` 即局部化。

## 结果（event 引擎，`rare_stride=1`，20k 人）

| cells | avg_ms | mean_acq |
| ---: | ---: | ---: |
| 1 | 10.21 | 2.82 |
| 16 | 9.91 | 2.82 |
| 256 | 9.56 | 2.81 |
| 4096 | 10.82 | 2.20 |

## 结论（如设计阶段所料）

**局部化并不带来数量级/亚线性提升**，只有约 **5%**（256 格时，来自更小的列表、更好的缓存局部性）；格子过细（4096）反而变慢，且因"碰不到人"使平均结识数下降。

原因在 Phase 5 已说清：**每 tick 的工作量 = 活跃个体数 × 单次成本**。局部化降低的是"单次成本"和"可分解性"，**不减少活跃个体数**。只要每个成年人以固定速率产生事件，总量就是 `O(人口)`。

**局部化的真正价值**是：① 更真实（人是和邻居交往，不是和随机陌生人）；② **格子彼此独立** → 是**并行化**（多进程/多核）的前提。单机顺序执行时它只是常数级优化。

> 要真正"容纳更多单位"，剩下的杠杆只有：**并行**（靠局部化分片，≈ 核数倍）或 **换层**（数组/C/Rust，常数 10–100×）。

# 均值场引擎（Measure Engine）· Stage 0–1 已完成

目标：让每 tick 的 CPU/内存**不随人口 N 增长**（支持 N→∞）。做法：把人口表示为**状态空间上的计数分布**（不做逐个体模拟），每 tick 施加桶间"流"。个体引擎原样保留作高保真参照。

## 设施（Stage 0）

- `bench.fingerprint`：分布指纹（年龄直方图、财富分位、度分布、基尼、均值）。
- `bench.convergence`：`compare_fingerprint`（各分量归一化到 0..1）+ 基线导出。
  - `python -m bench.convergence --individual 1000 10000 100000 --steps 300` → `bench/results/fingerprints/`

## 测度引擎（Stage 1）

模块：`app/core/measure/`（`space` 状态空间 / `measure` 稀疏计数 / `transitions` 流算子 / `engine`）。
- 状态：`(年龄段 0..120, 性别, 财富段[线性, 宽度=1000], 婚配)`。
- 流：衰老(每360tick)、收入(+1000/30tick)、死亡(age≥60, 0.05/360)、出生(已婚可育, 0.005/27)。
- 成本 = `O(占用桶数)`。

## 收敛验证（Stage 1，与"精简个体模型"对比）

`python -m bench.convergence --measure-compare --sizes 1000 10000 100000 --steps 2000`

| N | age_l1 | degree_l1 | gini_diff | wealth_rel |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.0079 | 0.0000 | 0.0028 | 0.0062 |
| 10,000 | 0.0047 | 0.0000 | 0.0012 | 0.0116 |
| 100,000 | **0.0008** | 0.0000 | **0.0000** | 0.0060 |

年龄分布差异随 N 单调收窄 → **测度引擎收敛于个体模型**。

## 关键指标：成本与 N 无关（Stage 1）

测度引擎单步耗时（本机）：

| N | ms/step | 占用桶数 |
| ---: | ---: | ---: |
| 1,000 | 0.257 | 508 |
| 10,000 | 0.441 | 890 |
| 100,000 | 0.561 | 1,147 |
| 1,000,000 | 0.667 | 1,367 |

**人口放大 1000×，单步耗时只涨约 2.6×，且随占用桶数趋于饱和**——这正是"可接近无限"所需的性质（成本由状态空间大小封顶，与 N 无关）。
对比：个体引擎在 1e5 时约 50ms/step，测度引擎约 0.56ms/step（~90×）。

## 已知边界（Stage 2+ 待做）

- Stage 1 无关系图、**无生育**（初始全未婚 → 测度层 somewhat degenerate）。婚姻/结友/生育在 Stage 2 折叠为度/边状态流。
- 财富**线性分桶**（宽度=1000）；超过 3000 桶（>3e6）会溢出到末桶，长跑需扩桶或改用自适应分辨率。
- 继承（Stage 3）与物化层（Stage 4）尚未实现。

# 均值场引擎 · Stage 2 已完成（婚配 + 生育）

把关系图折叠为"婚配可用性闭合"，重新引入生育。用 `FULL_FLOWS = (aging, income, death, marriage, birth)`。
```
python -m bench.convergence --full-compare --sizes 2000 5000 10000 --steps 4000
```

## 关键建模发现（诚实记录）

1. **个体模型里的婚配是"性别中立"的**：`spouse_event` 从 `friend+familiarity` 里挑任意 `18<=age<60` 单身者，**不检查性别**。所以不是"1 男 + 1 女"，而是任意两名单身者配对，且每桩婚事消耗 **2** 个单身者。
2. 婚配率受"可接触对象里至少一个单身"的可用性约束：`q ≈ 1-(1-p_elig)^deg`，`p_elig`=单身占比，`deg≈2.5`（对个体引擎稳态拟合）。
3. 我曾误用 `r·min(M,F)` 与 `r·(M+F)`：前者严重欠婚、后者过婚；性别中立的可用性闭合才是对的。

## 结果（FULL_FLOWS vs 完整个体引擎）

| N | steps | age_l1 | gini_diff | wealth_rel | married_diff | pop_ind | pop_mf |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2,000 | 4000 | 0.031 | 0.009 | 0.010 | 0.034 | 2070 | 2046 |
| 10,000 | 4000 | 0.027 | 0.005 | 0.014 | 0.019 | 10057 | 10148 |
| 5,000 | 6000 | 0.033 | 0.005 | 0.005 | **0.007** | 5333 | 5267 |

稳态下 **married/gini/wealth 差异均 <2%**；`age_l1≈0.03`（比 Stage 1 略大，来自生育时点与接触成形的瞬态差异，属均值场固有近似）。

> 边界：早期（t≈1000）均值场婚配偏快，因为个体需要数百 tick 先建立联系，而均值场假设联系即时可用。稳态误差很小。

# 均值场引擎 · Stage 3 已完成（继承与财富尾部）

新增继承算子：死者 10% 的财富转移给"子女"年龄段（年龄差 25），按人头均分。
`FULL_FLOWS = (aging, income, death, marriage, birth, inheritance)`。

## 关键工程发现（性能陷阱）

第一版继承用**分数桶位移**（把每个桶按 delta 的小数部分拆到相邻两桶），结果**每个 tick 把计数碎片化**：N=3000 跑 3000 tick 后 `occupied` 从 ~500 膨胀到 **19500**，单步耗时从 ~1.5ms 涨到 **77ms**（长跑必然卡死）。

修正：**按年龄段累积分数位移，攒够整桶时做整桶平移**（不碎片化）。修复后 `occupied` 稳定在 ~1200，单步 ~2ms。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| occupied (t=3000) | 19,512 | ~1,200 |
| ms/step (t=3000) | 77.3 | ~2.0 |

## 结果（含继承 vs 完整个体引擎）

| N | steps | age_l1 | gini_diff | wealth_ks | married_diff | gini_ind | gini_mf |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3,000 | 4000 | 0.034 | 0.0023 | 0.031 | 0.040 | 0.456 | 0.454 |
| 3,000 | 8000 | 0.030 | **0.0003** | 0.054 | 0.017 | 0.525 | 0.525 |
| 10,000 | 8000 | 0.026 | **0.0009** | 0.052 | 0.023 | 0.528 | 0.529 |

**基尼几乎完全吻合（差 0.0003–0.0023）**；财富分位曲线的最大偏差（KS）约 **3%–5.4%**，略过 5% 线。

## 关于 5% 通过线

- **基尼**：远超达标（差 <0.5%）。
- **KS**：3%（t=4000）→ 5.2–5.4%（t=8000）。原因明确：均值场把遗产**按人头均分给整个年龄段**，丢失了"富父母的子女继承更多"的**相关性**；时间越长、财富越分散，尾部误差越明显。这是均值场在财富尾部的**固有近似**（计划里预警过）。
- 若需更严的 KS：提高财富分辨率（缩小桶宽）或引入**家族物化**（Stage 4 的有限个体层）。目前**尚未触发**"必须家族物化"（基尼达标）。

## 成本（Stage 3 后）

测度引擎单步仍是 `O(占用桶数)`、与 N 无关；FULL_FLOWS 有 6 个流算子，故常数比 Stage 1 大（~2ms/step @ occupied≈1200）。

# 均值场引擎 · Stage 4 已完成（物化层）

| 1,000,000 | 2.477 | 985,092 | 965 | 1,430 |
| **10,000,000** | **2.452** | **9,851,099** | 965 | 1,430 |

**从 1 万到 1000 万个单位，单步耗时恒定在 ~2.45ms**；只有总人口数字在变大，物化窗口稳定在 ~965。这就是"可接近无限"的直接证据。

## 守恒与一致性（测试）

- capacity 强制：`len(窗口) ≤ capacity` 恒成立。
- 长跑（20000 步）总量只随"窗口个体的出生−死亡"变化（无泄漏）。
- 窗口的年龄分布与测度层一致（5000 抽样，L1 < 0.07，属有限样本噪声）。

# 财富尾部的闭合（Stage 7）：继承算子从"按人头均分"到"段池整数分配"

## 动机（先测量）

Stage 3 记录的 KS 突破 5% 线（3%→5.2–5.4%），当时归因"继承按人头均分丢失富→富相关"。
`bench.diagnose_tail`（新工具）先做归因：

```
python -m bench.diagnose_tail --n 5000 --steps 8000 --seeds 1 7 42
```

多种子结论（N=5000, t=8000）：

| 量 | 旧均值场 | 说明 |
| --- | --- | --- |
| KS（全部 21 分位） | 4.4 / 5.6 / 5.2 % | **被 p100 单点主导** |
| KS（排除 p95/p100） | 2.1 / 2.0 / 2.4 % | 稳定的系统性偏差 ≈ **这就是丢失的"富→富"相关性** |
| p100 相对偏差 | +5.2 % | 最大次序统计量，跨种子±0.6%——**一大半是采样噪声** |

即：文档里"KS 5%+ 全部归因继承相关性"高估了；系统性偏差 ~2.2%，p100 是噪声。
桶溢出也被排除（3000 桶上限的实测最高占用 = 295）。

## 两个账本教训（性能/正确性陷阱，诚实记录）

第一版"按财富质量占比分配遗产"用 per-bucket index 记欠账（pending，桶单位）：

1. **复用桶索引的账本会凭空注水**：欠账记在桶上而桶会换主人/被其它流合并——
   新住户继承旧住户的欠账，整桶平移时按"全部人头×整桶宽度"支付 = 超付。
   财富守恒审计（初始+收入−蒸发 vs 期末报告值）抓到 **+1.39e8 注水**。
2. 欠账"随人走"（衰老/收入/平移都搬运 pending）在理论上是好账本——但
   **合并桶内不同人群的 per-head 权益无法用一次整桶平移精确支付**（少付 = 亏欠，
   多付 = 注水），要想精确必须按子群分数拆分 → 正是 Stage 3 记录过的碎片化灾难。

## 最终设计（无 per-cell 账本）

- **段池**：每个死者 10% 财富按 gap 窗口 `u∈[a-50, a-18]`（生育对 18–50 岁父母
  近均匀 → 差值密度均匀）注入 `measure.yearly_inherited[u]`；
- **年批清算**（每 360 tick）：对每个非空段，按接收桶**财富质量占比**分配理想份额，
  每桶只支付 floor() 得到的**整数桶位移**（整桶平移，不拆分计数），**余量留池**下年再分；
- 守恒：池只进（遗产 0.1）出（支付 ≤ 理想份额绝对不超付），审计误差 0.06%
  （= 桶中心 vs 整数位移的量化噪声）；
- 成本：O(占用桶数)/年，N 无关性保持（1e6 人口 2.47ms/step，occupied 1379）。

## 结果（多种子，N=5000, t=8000）

| 指标 | 旧（按人头均分） | 新（段池整数分配） |
| --- | ---: | ---: |
| KS 中位 | 5.21 % | **2.73 %**（最好 0.98%） |
| p100 偏差 | +5.21 % | +1.89 % |
| mf/ind 总财富 | +5 % | **+0.7 %** |
| p70–p95 逐分位 | +1~+2.9 % | **±1 % 以内** |

gini 差 ≈0.009（mf 稍扁，受桶中心量化的加权 gini 影响）——低于 Stage 3 的 0.02 线。

## 结论

- "富→富相关性"用**段池+质量占比+整数支付**即可闭合，**不需要**家族物化；
- p100 是次序统计量，跨种子 ±0.6% 的摆动应作为"有界采样噪声"记录，不应作为调优目标；
- 两个账本教训是均值场算子设计的通用约束：**账本只能挂在"不会易主的键"上**
  （这里=不用账本），任何"分数桶位移"都必须换成"整数支付+留池"。
